# Replace the coordinator with native workflows

Status: design study, not implementation approval. Date: 2026-10-29.

## Decision summary

Recommend **B: versioned delivery subflows with a portfolio run view**. TUIC owns scheduling, attempts, evidence, decisions, integration and recovery. An AI remains a re-entrant decision worker, not the process scheduler. Fabbrica can place execution on machines; it must not implement a second workflow engine.

Option A exposes every delivery step in one graph. It is useful for an initial parity pilot, but duplicates policy when several repositories need the same chain. Option B uses the same engine and explicit nodes, with pinned delivery subflows and repository policies. It provides a compact portfolio view without hiding the evidence inside an opaque “delivery” box. Both options replace the coordinator; neither keeps a permanent shell coordinator beside TUIC.

This study changes documents and static mocks only. It creates no stories, changes no product behavior, runs no delivery pipeline, and authorizes no merge, push, release or app restart. Review pack and Validate pack are excluded.

## 1. The thing being replaced

Today the coordinator is a scheduler, a durable-state substitute, an integration operator, a proof auditor and a conversational decision maker. A node labelled “Coordinator” that simply runs the existing scripts would move the terminal without replacing that system.

The replacement has four layers:

1. **Definition:** immutable graph revision, node configuration, edge outcomes and versioned policy references. Draft edits use expected revisions. Runs pin the full transitive definition/policy set.
2. **Run:** event ledger, branch tokens, attempts, effects, questions, budgets, resource reservations and proof obligations. No TSV or chat transcript is authoritative.
3. **Adapters:** agent harness, command execution, Git integration, worktree lifecycle, evidence store, notification and machine placement. Deterministic tools remain executables when appropriate; scheduling and correctness rules do not remain shell glue.
4. **Views/API:** editor, live graph, run queue, evidence inspector, decision digest and cursor-ordered history. AI Chat, desktop and remote/browser clients use the same backend transitions.

The chain has two different gates. **Pre-land checks** validate the proposed merge artifact and permit integration. **Post-land gates** discharge mutation/coverage/CRAP and aggregate-suite obligations on a pinned batch artifact. A green critic alone is neither. A landed story may be “integrated, proof pending”; it is not release-ready until applicable obligations pass. The mocks retain implement → critic → land → gate → post-landing batch tests, with pre-land admission shown inside the integration step.

### Vocabulary and status legend

- **Author:** configurable Agent node, not one hard-coded Research/Planner type.
- **Run command:** deterministic process effect with a typed receipt, not a shell string guessed by a model.
- **Integrate:** typed Git operation under a canonical-repository lock; not an unrestricted command node.
- **Judge:** evidence-based yes / no / uncertain decision.
- **Gate:** deterministic policy pass / fail; an optional approval request is an asynchronous wait associated with the gate, not a PTY prompt.
- **Ask:** durable question with an answer schema and branch-local suspension.
- **Fork / all-Join:** create and reunite correlated branch tokens. Existing Join remains an exclusive merge and must be named as such.
- **covered:** the current native service provides the named core semantic. It does not mean this complete coordinator migration already exists.
- **missing:** some required rule, configuration, adapter or view is absent; the row names the replacement target.
- **to remove:** retire the coordinator-specific mechanism after parity; retain the underlying requirement at its named destination. Never delete it during this study.

The exhaustive mapping register at the end is part of this document. It includes tools beyond the four specifically requested directories so that build, remote, health, reports and upkeep are not silently omitted. Test files, fixtures, generated state and compiled caches are not coordinator scripts; they become migration acceptance fixtures, not runtime nodes.

### Critic triage and rule conflicts

Port `tools/agents/critic-triage.md` as a deterministic ordered policy, not a prompt suggestion. Scores remain judgement; malformed input is unresolved rather than PASS. First matching rule wins:

| Order | Condition | Outcome |
| --- | --- | --- |
| 1 | risk = 5 | FIX at any effort |
| 2 | adds a mechanism | STORY if value ≥ 3, otherwise ACCEPT |
| 3 | deletes only and effort ≤ 2 | FIX |
| 4 | risk 3–4 and effort ≤ 3 | FIX |
| 5 | value − effort ≥ 2 | FIX |
| 6 | value ≥ 3 | STORY |
| 7 | otherwise | ACCEPT with named risk |

Only FIX findings enter the repair activation. STORY creates a bounded proposal for separate work, not unauthorized scope growth. Round 2 checks prior FIX findings and scores new findings by the same rules. After the total-review cap, request a decision among the smallest fix, explicit accepted risk or abandonment. Risk acceptance cannot manufacture a passing required check or integration receipt.

The source register preserves contradictory historical instructions intentionally so migration can resolve them explicitly:

- Global orchestration remains the only model-routing authority. Obsolete repository model tables are not imported as executable policy.
- Managed story instructions prohibit per-story GREEN/full suites while critic and batch briefs require their own checks. Model these as different phases with one explicit validation owner, not one ambiguous universal test rule. A task-specific authorized Rust RED/clippy rule remains task-specific.
- The old native plan excluded arbitrary shell nodes in its first release. The requested Run command node is a new proposed capability, requiring approval and a typed execution contract; it is not claimed to exist already.
- Same-project Story Dispatch concurrency already exists; Fork/all-Join adds within-graph branch semantics. Portfolio scheduling must not raise the existing per-run bound implicitly.
- Stop-hook minimum staffing is not a correctness condition for delivery and cannot override the global delegation gate. Retain ownerless-work alarms and optional capacity targets, remove forced headcount as a prerequisite for an AI ending its turn.
- Current source overrides stale README statements about Gate publication and persistent critic counters. Before implementation, pin source policy digests and resolve any remaining contradictory rule with Boss rather than blending both.

### Branch and failure semantics

Proposed token key: `(run, execution, fork_activation, branch, generation)`. A branch-local wait carries that key. Only explicit run-wide pause/cancel, a shared safety stop or an uncertain shared effect stops unrelated work. A lease loss on one remote read-only check blocks that branch; uncertainty about a canonical merge locks that repository's integration lane, not every repository.

Fork publication requires its matching join region, declared all/selected-arrivals semantics, reachable terminal outcomes and bounded dynamic fan-out. Default all-Join does not mean quorum. Uncertainty cannot disappear through an optional branch. If a branch is canceled, its join outcome must explicitly propagate blocked/canceled or use a published optional-branch rule. Preserve old exclusive-Join replay semantics; parallel tokens need a new event-contract version, not reinterpretation of old events.

The current plan concurrency default is two with configurable one to eight attempts. The coordinator's staffing target defaults to ten. These are different policy domains: portfolio capacity can schedule multiple plan runs, while each run stays within its configured cap. Do not silently raise engine limits or assume a graph Fork solves cross-project admission.

## 3. The AI coordinator's new role

### A complete operating cycle

1. Boss requests delivery or an opt-in event arrives. AI resolves the project, approved story/plan and published definition, then calls the existing `workflow action=run` start_graph boundary with a stable request ID and expected revision. Definitions are currently HTTP/IPC only; a matching definition-management MCP action is a proposed gap, not an existing tool.
2. The daemon validates prerequisites, claims work, assigns isolated worktrees and starts admitted nodes. The AI does not generate a queue script or keep a watcher alive.
3. The AI reads the scoped run snapshot and `events` after its last acknowledged cursor. Notifications contain IDs/cursors, not the only copy of a report. If the AI session disappears, the daemon continues deterministic work; a replacement reads the same durable state.
4. Routine transitions are policy. Critic findings are scored, then the deterministic triage policy selects FIX/STORY/ACCEPT. A reviewer remains separate from the implementer. Failed checks cannot be overridden by optimistic prose.
5. An uncertain Judge edge produces a decision task. The AI reads the exact evidence, can call read-only advisors under the global model policy, and proposes a typed resolution. Reserved/destructive/product choices go to Boss in a digest. Split advisor votes go to Boss. Advisor requests have their own bounded fan-out and receipts.
6. Ask and approval tasks live in an inbox/digest accessible by AI Chat, desktop and browser. A proposed answer includes the question revision, subject digest and decision ID. The daemon validates it, appends the event and wakes only the dependent branch. Boss can answer later; other work keeps running.
7. Integration, proof gates and batch tests are daemon-owned effects. The AI handles conflict repair or ambiguous external state, not every normal shell exit. Completion requires all pinned obligations and scope closure, not an empty ready queue.

Current APIs support start/read/events/commands, typed managed reports and explicit input answers, but current NeedsInput is run-wide. Branch-local decision resolution, definition editing from MCP, native integration and ACP coordinator parity require implementation. The managed launch documentation requires an active owning PTY coordinator for worker launches. TUIC AI Chat ego has no PTY; its host-issued peer identity must be supported explicitly at this boundary. Do not fake a terminal identity or route it through parser state.

### What AI gains

- Its context holds decisions and deltas, not children.tsv, gate debt, polling output or shell quoting rules.
- Retry/cancel/restart correctness is enforced without the AI remembering a sequence of scripts.
- One source of truth supplies live operator visibility, evidence and cost.
- Rules such as “two reviews” are validated draft edits followed by publication. A running v3 remains on v3; v4 applies to new runs. Migration of an active run is a separate explicit, audited action, not a draft side effect.
- Work continues when Boss or the AI is unavailable. Uncertainty remains visible instead of becoming a silent stop or an unsafe replay.

## 4. Options and consequences

### A — Explicit delivery graph

A graph exposes Implement, Critic, Judge, repair loop, Integrate, proof Gate, aggregate suite, Notify and End, with explicit Fork/all-Join around independent stories/checks. Repository policy is selected on each applicable node.

**Benefits:** smallest conceptual jump; every step visible; straightforward comparison with today's scripts. Good initial parity harness. **Costs:** repeated node/policy configuration across projects; large graphs; batch and portfolio relationships are harder to edit safely. A changed critic policy must update each draft or a shared pinned policy reference. **Risk:** a visually simple graph can conceal duplication if each Run command merely invokes the old coordinator.

### B — Pinned delivery subflows and portfolio view (recommended)

A portfolio delivery workflow dispatches independently scoped story subflows, waits for integration and batches proof obligations per repository. Each expanded subflow is the same explicit chain as A. Subflow version, policy version and artifact are visible. A Call node pins a definition revision; it is not an opaque shell macro. Cross-project dependencies refer to verified integration receipts at owning daemons.

**Benefits:** one useful edit changes the delivery template for future runs; compact portfolio visibility; separate story, integration and proof lifecycles; portable execution adapters. **Costs:** adds pinned Call/subflow authoring, nested navigation and portfolio aggregation. More implementation than A; needs explicit ownership for questions, costs and cancellation across parent/child runs. **Risk:** a hidden subflow becomes a new invisible coordinator unless expansion exposes every activation, receipt and exception.

**Recommendation:** implement common runtime contracts first and pilot the explicit chain as A; make B the operator-facing replacement once parity passes. This is staged delivery of one engine, not two schedulers. Do not start with a general BPMN platform, unrestricted shell palette, external workflow server or a Fabbrica rewrite.

Decision for Boss after the study:

- [ ] A — expose the complete graph first; accept repeated project configuration while proving replacement.
- [ ] B — approve pinned delivery subflows and the portfolio run view; use A's explicit chain as the first executable subflow.

Neither checkbox grants implementation authority in this study.

## 5. Distributed execution and Fabbrica portability

**Can a node run on tuic-remote?** Current WorkflowRuntime is created on headless as well as desktop boot, so a workflow owned by that daemon can execute supported local nodes. This is not evidence that one existing graph can place individual nodes on several machines. Current required checks execute in the assigned local worktree. A remote target selector and cross-machine effect binding remain missing.

Proposed execution port:

- Input: execution/effect ID, generation, pinned source artifact, argv or prompt/profile, scope, environment-secret references, capability/target requirements, timeout, cancellation and resource keys.
- Output: accepted/queued/running/terminal/uncertain receipt, executor identity and fence, command/prompt digest, source/target/toolchain, exit/outcome, artifact/log digests, usage and stop proof.
- Owner: one TUIC run ledger decides graph transitions. An adapter submits and reconciles effects; it never chooses successor edges. Lost replies use the same effect ID. Unknown external state is reconciled before replacement.

Local adapters preserve today's division: Rust checks on rb; JS/TS on the local machine; native GUI/platform checks only on a matching target. A Linux success never certifies a macOS-only path. No host paths are embedded in reusable definitions: resolve repository/workspace and artifact IDs at the executor. Credentials stay in executor/broker stores, never prompts or receipts.

Fabbrica owns enrollment, mTLS machine identity, placement, capacity, leases and quarantine. TUIC owns sessions, worktrees, graph policy and local execution. F SPEC C4 describes thin Unix adapters for workflow definition/run actions and stable launch keys, plus bounded native evidence; C3/C5/C6 describe worker/credential/stop boundaries. Preserve their task/generation/fence tuple together with TUIC run/execution/activation/effect IDs. A Fabbrica task handle is not a TUIC workflow run ID.

A partition cannot authorize another merge or provider action just because old results are fenced. Keep the old task quarantined, retain its slot, revoke scoped credentials and obtain owned-execution stop proof before retry. Cancellation is a request until observed; cleanup follows acknowledged result/stop proof. Keep one canonical Git integration owner; do not mount or concurrently mutate Boss's live checkout on remote workers.

Portable parts: graph definition, triage/quality policy, event/receipt schemas, agent report contract, branch-local decisions, template pinning and evidence freshness. Adapter-specific parts: rb admission/transport, Docker/cache setup, path mapping, GUI/device access, secret delivery and local build cache. Fabbrica should reuse the TUIC definition and run APIs, not copy Rust reducer semantics into Go. Ship a versioned portable definition format only after its ownership/versioning contract is agreed; the old native plan explicitly excluded import/export, so this study does not silently add it to the current feature.

## 6. End-to-end parity trial (after implementation approval)

No parity trial ran in this study. Static mocks prove layout and local interactions only. They cannot prove delivery, recovery, cost or cluster execution.

### Paired real-story protocol

1. Select approved real stories before implementation: a small fix with pre-fix RED, a TS interaction with consumer checks, a Rust shared-contract change, a two-story dependency, a disjoint parallel pair, a merge-conflict case and a batch with a mutation survivor. Use actual story IDs/requirements captured from the store; do not invent synthetic “real” stories. Historical 2351 and 2451 are evidence sources, not automatically eligible open work.
2. Snapshot each requirement, criterion revision, base commit/tree, dependencies, fixtures, policy, toolchain, target and exact model profile. Budget both lanes equally and record environmental differences.
3. Run the current coordinator chain and the native workflow on isolated clones from the same base and equivalent story snapshots. Only one lane may land into a trial canonical ref at a time; neither touches production main. Disable pushes/releases and external publication in both lanes. Give each lane fresh equivalent agent context, then alternate lane order across pairs to reduce warm-cache/order bias.
4. Compare independently produced outcomes against the same acceptance oracle, not byte-identical patches. Record different but valid implementations. Reviewers do not inherit the other lane's answers. Preserve every failure and iteration; never discard a red trial from timing/cost totals.
5. Exercise the full chain: implementation → independent critic → triage/repair → merge-result admission → integration receipt → post-land gate → pinned aggregate Rust/local Vitest → story/plan closure → cleanup. Include local JS and remote Rust evidence, matched-test counts and strict clippy.
6. Inject at least one crash before/after effect commit, lost spawn response, duplicated report/answer, stale review after edit, trunk movement during checks, idle/dead child, blocked Boss question, resource freeze and remote lease loss. Use isolated owned processes only. Demonstrate that an unanswered question does not delay a disjoint story, while dependent work correctly waits.

### Comparison ledger and acceptance

| Dimension | Record per pair, each lane | Pass condition |
| --- | --- | --- |
| Outcome | Criteria, implementation commit, canonical result, dependency release, scope deviations, cleanup | Every criterion meets the same oracle; no unauthorized action, data loss or stale dependency release. |
| Proof | Pre-fix RED failure, final GREEN, critic identity/artifact, triage, checked merge tree, obligations, mutation/CRAP/coverage, native evidence, omissions | No proof present in the current chain is lost; unknown/stale evidence never appears green. |
| Time | End-to-end wall time, active work, queue/wait, Boss response, recovery, repeated checks | Native no worse than baseline on the agreed matched comparison; show raw pairs and queue-normalized values, not only averages. |
| Cost | Provider-reported money/tokens including coordinator/advisors/rework, unmeasured subscription usage, machine seconds and duplicate tests | Native no worse on measured dimensions; missing usage prevents a cost-parity claim, not a zero charge. |
| Human interventions | Each decision, restart, manual script, merge, repair or cleanup with reason and minutes | Native no more interventions, and none needed merely to reconstitute scheduler state or answer a globally blocking question. |
| Visibility/control | Can Boss locate pending question, rule, cost, artifact, failure, running node and recovery action without chat archaeology? | Editor publishes a cap change without script edits; active run stays pinned; live view and replay agree after reconnect. |

Start with one small paired story, then the disjoint pair and complete case set. Agree the observation window and acceptable environmental normalization before collecting results; do not invent a numerical tolerance after seeing regressions. If a metric is worse, diagnose the responsible node/policy, change a draft, publish a new revision and rerun the affected paired case plus invalidated scenarios. Retain revision-to-revision comparisons until the workflow is at least equal on every required dimension. A single good run cannot compensate for a missing proof or global question block.

### Retirement and cutover

Before cutover, every **missing** mapping row needs an implementation receipt or an explicit Boss-approved removal; every **to remove** row needs a tested replacement invariant. A dry-run inventory must show no obligation owned only by a TSV, result-file scan or coordinator context. Import/reconcile active work with explicit operator approval; never infer successful old effects. Drain old pumps and landing writers, then switch each project to one workflow owner. Keep old scripts read-only for rollback evidence, not running in parallel.

Rollback stops new native dispatch, preserves all ledgers/artifacts and reconciles active/uncertain effects before an old coordinator takes ownership. Do not automatically replay a failed native run through the old scripts. A run that has already merged remains merged even if its cleanup failed.

### Semantic rule destinations

The detailed rule register below uses these policy families. All are proposals unless marked covered by an explicit source above:

- **P-agent:** global role/model authority; isolated worktree, owned scope and live-store rights; typed report; no child coordination; prompt provenance; resume only after reconciliation.
- **P-proof:** independent critique, seven-rule triage, exact RED subject, consumer scope, one batch owner, fresh check/merge receipts, never hide failure, native-target disclosure.
- **P-integrate:** one canonical writer, expected base/source, protected live checkout, no stash/discard/force cleanup, partial-success journal, post-land debt.
- **P-resource:** build/GUI/device admission, machine freeze, one mutation process, bounded process ownership, caches and disk pressure.
- **P-decision:** asynchronous digest, Boss-reserved authority, advisor escalation under global routing, first valid answer, no timeout consent.
- **P-observe:** scoped MDKB-first retrieval, bounded cursor snapshots, truthful unknown/stale status, retained evidence and usage.
- **P-maintain:** timer-triggered triage, reports, release readiness, safe cleanup, durable follow-ups; no effect inferred from age.
- **P-runtime:** payload-bound IDs, durable disposition, generation fences, event-driven work, crash recovery without uncertain replay (core ledger is covered; coordinator-specific completion remains missing).
