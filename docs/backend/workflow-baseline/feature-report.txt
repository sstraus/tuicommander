## Scope and evidence

The orchestrator is a workspace, operating rules, skills and scripts. TUICommander supplies sessions, mail, repository actions and scheduled jobs. Application development takes place in the target repository, not here.

This is a source inventory, not a live health certificate. **In use** means a current rule, configured hook or source caller selects the capability. **Partial** means an optional integration, an external installation not checked here, or a stated limitation. **Unused** means not selected by the named current entry point, not proof that nobody ever calls it. **Broken** requires decisive failure evidence; this audit did not execute operational commands to find failures. A test file is evidence of intended protection, not evidence of a passing run today.

MDKB was queried first: `mdkb search 'orchestrator tools capabilities operations hooks' --root orchestrator --limit 15`. It returned related reports and `orchestration.md`, not a complete tool inventory. The audit therefore inspected the requested rules, decisions, skill instructions, hook configuration, and script headers, commands, functions and callers. Tests and fixtures are validation support, not separate user capabilities. Generated `.wiz` state and Python bytecode are not entry points.

Paths below are relative to the repository root, except named home-directory policies. The entry point is also the implementation evidence. The final column records the caller, rule or limitation. “Manual” means the coordinator or an authorized agent invokes it; it does not mean Boss must run it.

- **I1 — Duplicate and stale critic documentation.** `tools/README.md` has two incompatible `critic-brief.sh` signatures. The implementation accepts `<repo> <story> <worktree> <round> [focus]` and loads `critic-brief.template.md`, not `briefs/critic.md`. Reconcile the index and retire the unused template only after confirming external users.
- **I2 — Digest paths contradict persistent delivery.** Open-asks and worktree-triage skills still write under `~/Gits/.tmp/boss/`. Boss operating rules require persistent bilingual reports under this repository because mobile cannot open untrusted temp paths. Update both skills and preserve/apply existing ticks before moving any live digest.
- **I3 — Worktree skill cleanup instructions are stale.** The worktree-triage skill still ends with raw Git worktree/branch deletion and allows direct low-risk landing. Current managed rules require TUIC tracking, child-close ownership and the selected review flow; operations also says every branch needs a critic. Reconcile before the next destructive triage, without discarding existing work.
- **I4 — Routing and validation rules have several competing copies.** Global policy is authoritative, but spawn roles, legacy generated guides and local templates contain other routing defaults or admission limits (for example Luna is implemented but not admitted by `spawn-roles`). Per-story RED/strict-clippy rules, deferred GREEN rules and batch retrospective RED instructions also differ across managed rules and templates. Keep one authoritative contract and make wrappers/templates derive it; do not resolve this by silently choosing a cheaper gate.
- **I5 — Countdown output still contains a cross-release total.** `release-countdown.sh` ends with an `all:` line, but Boss rules require separate release lines and never one combined total. Per-release calculation exists; remove or explicitly separate the unwanted presentation only in a scoped tested change.
- **I6 — Mutation documentation understates current implementation.** README still says the current-measurement protocol fixture/end-to-end work is pending as of 3 October. The repository now contains `rb-current-measurements.py`, the producer fixture and `rb-current-measurements-e2e.test.py`. - **I8 — Hook coverage differs by CLI.** The local Claude and Codex hook files select different guards; no-pkill and no-zsh-path are present without local wiring. Verify the effective global/runtime installation and document coverage, rather than assuming one configuration protects every harness.

A separate read-only installation/last-run audit would establish actual in-use, broken or unused runtime status. This report intentionally makes no such runtime claim.
